# Testing

## 1. Principles

1. **Business logic is tested first.** Money, references, state machines, Wompi crypto and
   check-in decisions are pure functions tested in isolation — fast, deterministic, no network.
2. **Fail safely is a requirement, not a nuance.** Tests assert the _rejection_ paths too: unknown
   statuses, tampered payloads, mismatched amounts, unexpected API shapes.
3. **No external service is ever contacted.** The Wompi and Resend clients take an injected
   `fetch`; signatures are verified against the official documented vector and against an
   independent SHA-256 implementation.
4. **Fixture data is synthetic.** No real personal data, no real credentials, in tests or in docs.
5. **Guardrails are tested too.** Version parity between npm and Deno configs, `.env.example`
   completeness and repository secret hygiene are automated, because they are the kind of thing
   that silently rots.

## 2. What runs where

| Suite                                               | Command                                     | Runtime                                   | Needs Docker? |
| --------------------------------------------------- | ------------------------------------------- | ----------------------------------------- | ------------- |
| Domain + integrations + config + tooling            | `npm test`                                  | Node 24 (Vitest)                          | No            |
| Migrations applied to a real Postgres               | included in `npm test`                      | Node + PGlite (Postgres in WASM)          | No            |
| Edge Function typing                                | `npm run functions:check`                   | Deno 2                                    | No            |
| Everything                                          | `npm run check`                             | all of the above + lint + format          | No            |
| Phase concurrency races                             | ad-hoc script, recorded in the phase report | real PostgreSQL 17, two parallel sessions | **Yes**       |
| Local Supabase stack, PostgREST policies, `db diff` | `npm run db:reset`, `npm run db:lint`       | Docker                                    | **Yes**       |

`npm run check` is the gate for every phase and every deploy; the Docker-dependent checks are run
manually (or in CI with a service container) before touching sandbox/production.

## 4. Adding tests

- New domain rule → unit test in `tests/domain/`, asserting both the happy path and the rejection.
- New Wompi behaviour → assert the **documented** input/output (cite the doc section in a comment).
  If the docs do not cover it, the code must fail safely and the test must pin that behaviour.
- New confirmation/payment behaviour → assert all three layers where relevant: the domain rule,
  the SQL function (schema suite) and the handler outcome (api suite). A rule that exists in
  only one of them is a drift waiting to happen; `payment-status`/`payment-confirmation` contain
  explicit parity assertions between the TypeScript ranking and the SQL function.
- New migration → the schema suites pick it up automatically; add assertions for new enums
  (`enum parity`) and for any constraint you rely on. If the migration touches privileges or
  RLS, extend `schema/rls.test.ts`; if it changes a uniqueness guarantee, add a behavioral
  rejection test in `schema/constraints.test.ts`; if it adds or changes pricing/order logic,
  extend `schema/pricing-parity.test.ts` so the SQL and TypeScript rules stay in step.
- Concurrency-sensitive change → also run the two-session race by hand against a real PostgreSQL
  (the command sequence is in the phase report) and record the result there.
- Schema tests must assert the _behavior_ (a duplicate is rejected, a bad value is rejected),
  not only the definition. A constraint that exists but is misdirected protects nothing.
- New secret or config variable → update `.env.example`; the tooling suite fails otherwise.
